# Koru — Threat Model (STRIDE)

- **Scope:** Threats against Koru **itself**: blinding, misleading, or evading Koru, stealing its data, or gaining privileges through it. Attacks on the server Koru protects are Koru's detection scope and are not this document's subject.
- **Updates:** Updated whenever a change affects security (see [architecture](architecture.md#security)). Each row states the current status.
- **Basis:** [architecture](architecture.md), ADR-0001 to ADR-0010 in [docs/adr](adr/), `lab/lima/koru-lab.yaml`. External sources are in §8.

**Status values:**

- **OPEN:** A mitigation is planned but not yet implemented or proven.
- **MITIGATED:** The mitigation is implemented and has evidence. Its scope is written in the row; residual risk is in §6.

## 1. System summary

- **Workspace:** the Rust workspace (`rust-toolchain.toml` 1.99.0, `Cargo.lock`) with koru-event (event schema v1, `Untrusted<T>`, traits); koru-pulsar (embedded bridge module and translation pinned to Pulsar main `0bb7bc2`; ADR-0003); koru-decoy (decoy and breadcrumb generation from TOML templates, safe install, integrity record, clean removal, `DecoyCatalog`; ADR-0004); koru-detect (Sigma-compatible rules, enrichment, actor kind, allowlist and self-protection; ADR-0005); koru-store (SQLite WAL, schema validation and a reject counter at ingest, deduplication, JSONL and OCSF 1.9.0 export, IP masking, retention and rotation, data quality report; ADR-0006); koru-notify (ntfy, Telegram and SMTP channels; TLS via rustls + ring with the system certificate store; text sanitization and injection defense; per-channel rate limit and summarizing; an atomic, safe persistent queue on disk; exponential backoff and jitter; Healthchecks heartbeat; environment and `.env` settings; ADR-0007); and the `koru` command-line tool and `koru-agent` (Koru modules running in the same process via Pulsar's `pulsar_daemon_run` + `add_module`, root, eBPF; ADR-0008).
- **Data files:** `packages/` (decoys, rules, agent signatures) and `schemas/`.
- **Supply chain and CI:** `cargo xtask dependency-check`, `deny.toml`, GitHub CI on x86_64 and arm64 (ADR-0002), a signed release with an SBOM (ADR-0008).
- **Lab:** the Lima lab VM (`lab/lima/koru-lab.yaml`; no mount from the host, the repo is copied one-way with `lab/lab.sh sync`), the official Pulsar v0.10.1, time sync via NTS, gitleaks auditing.
- **Product site:** a separate web presence (Cloudflare Pages + Workers + D1) that is not part of this repository.

|---|---|---|---|---|

| V10 | Release signing key (`KORU_SIGNING_KEY`) | `.env` or GitHub secret | If captured, fake releases can be signed | Confidentiality, integrity |

## 3. Trust boundaries

| ID | Boundary | Description |
|---|---|---|
| GS1 | Kernel/eBPF ↔ user space | Pulsar's eBPF probes collect events from the kernel; Koru modules read them from Pulsar's bus. The Pulsar engine API runs unauthenticated on `/var/run/pulsar.sock`; the only protection is socket permissions (ADR-0001). |
| GS2 | Attacker-controlled event fields | File names, command lines and environment variables are the attacker's. They live under the `Untrusted<T>` type and the `x-koru-untrusted: true` marker in the schema ([architecture](architecture.md#event-model-and-data-quality)). These fields flow into the store, into notifications, into CLI output and, in a planned AI-assisted triage feature, into an LLM. |
| GS3 | Data files and dependencies from contributors (supply chain) | Decoy templates, rule packages and agent signatures come from contributors. Crates and the Pulsar git dependency come from outside. |
| GS4 | Outgoing notifications and heartbeat | ntfy, Telegram, SMTP and Healthchecks are third-party services. |
| GS5 | Lab VM ↔ Mac | Lima SSH, the one-way rsync copy of the repo from the Mac to the VM over that SSH (`/koru`; no mount, see KT-38), and the VM's network access. |
| GS6 | GitHub CI | Actions runners, secrets, release publishing. |
| GS7 | Internet ↔ product site | Cloudflare Worker and D1. |

## 6. Lab security

**Current state (`lab/lima/koru-lab.yaml`):**

- Lima's default home-directory (`~`) mount is absent; the template does not import Lima's default templates.
- No directory is mounted from the Mac (`mounts: []`, KT-38). The repo is copied one-way by `lab/lab.sh sync` over Lima SSH into `/koru` in the VM; the paths in `lab/sync-filter.txt` (`.env`, `.env.*`, `.git`, `target/`, `node_modules/`, `.wrangler/`, `.dev.vars*`, `data/real/`, `.DS_Store`) are not copied. If a new kind of secret file is added to the repo, it is added to the filter and `lab/scripts/sync-test.sh` is extended.
- Automatic guest-to-Mac port forwarding is off.
- The reverse direction (from the guest to the Mac's 127.0.0.1 via 192.168.5.2 / `host.lima.internal`) is blocked only by an in-guest nftables rule. This is not a trust boundary; anyone root in the VM can remove the rule (KT-37).
- SSH agent and X11 forwarding are off; `~/.ssh/*.pub` is not copied into the VM.
- Rosetta, containerd (nerdctl) and graphics output are off.
- The VM user is `koru`; it carries neither the Mac username nor the full name.
- The Ubuntu cloud image is pinned by digest.
- Time is taken only from NTS sources.

**Outbound traffic:** outbound traffic in the lab VM is open by default, which package and Pulsar installation need. It must be closed before attack tools or the AI attack agent run (KT-39).

**External-network isolation of the attack tools:**

- By default all outbound traffic is rejected; only the LLM API endpoint is allowed.
- If isolation cannot be provided, the attack tools and the AI attack agent do not run.
- Verification: before the attack tools run, show that an external connection attempt outside the allowlist fails.

**Open item to close before attack tools run: KT-37 (the reverse direction).** In Lima usernet the guest reaches the Mac's loopback address via the gateway. The interim measure is inside the guest and can be removed by root. It is closed and proven on the Mac side, with a control the guest cannot change (e.g. a separate unprivileged macOS user, a separate `LIMA_HOME`, a pf rule blocking that user's outbound connections on lo0 except Lima DNS ports). Because this work touches the Mac's system settings, it is a manual administrator step.

**Note (the Mac's LAN address):** the KT-37 interim measure closes only the path to the Mac's loopback. Services on the Mac bound to 0.0.0.0 (all interfaces) are also reachable from the guest via the Mac's LAN address; the guest sees them like any LAN device. For example, macOS's AirPlay receiver is reachable from the guest on ports 5000 and 7000. This path is closed, together with the other LAN devices, by the KT-39 outbound-traffic restriction (allowing only the LLM API endpoint).

**KT-38 (`.env` readable from the VM over the read-only mount): MITIGATED.** The mount is removed; `lab/lab.sh` copies the repo to the VM with rsync excluding `.env` and `.git`, as proven by `lab/scripts/sync-test.sh`. How the LLM key is given to the VM is in KT-40.

**Out of scope and accepted risks:**

- An attacker with root and the ability to load code into the kernel can blind Koru. In that case the goal is to leave a trail outside via the heartbeat break (KT-32, KT-33).
- Healthchecks pings are unauthenticated; a root attacker can read the URL and send fake pings (KT-03). Recording the reading of `.env` as an event reduces this risk but does not remove it.
- A root attacker can change the notification queue (KT-69) and the system certificate store (KT-70); those layers provide no protection against root. The goal again is to leave a trail outside: the heartbeat breaks (KT-72) and the findings have already gone to the store and the channels.
- Escape from the hypervisor (Apple Virtualization.framework) and Lima.
- The web layer (WAF, bot protection) is Cloudflare's field.
- Catching the use of a fake credential outside the server (usage detection) is not part of the current scope; see the [roadmap](../README.md#roadmap).

## 7. Most critical open items

1. **KT-37:** the reverse direction from the lab to the Mac's loopback. The in-guest interim measure is not a trust boundary; it must be closed on the Mac side before attack tools run.
2. **KT-39:** outbound traffic in the lab. If it is not closed, attack tools and the AI agent reach the internet.
3. **KT-40:** how the LLM key reaches the VM without the attack agent being able to read it.

Previously critical and now mitigated: **KT-38** (`.env` readable in the lab over the read-only mount; the mount was removed and the repo is copied excluding `.env` and `.git`) and **KT-30** (the bus feedback loop; closed by the translation test and the bridge module's design).
